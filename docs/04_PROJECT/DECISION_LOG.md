# Purpose

To record significant technical decisions made during implementation, why they were made, and what alternative was rejected. This is a historical record, not a standard — it explains the reasoning behind decisions already reflected in `docs/01_ARCHITECTURE/` and `docs/04_PROJECT/CURRENT_STATE.md`, it does not itself impose new rules.

# CTO-059

**Title**: Client as the top-level aggregate above Project
**Sprint**: F6-S01
**Decision**: Introduce a `Client` aggregate as the top-level business entity. Every `Project` belongs to exactly one `Client` (required foreign key). The workspace hierarchy becomes `Client → Project → Audit`.

**Why**: The platform is used by agencies managing several customers at once. Without a Client aggregate, every Project was an unowned, flat entity with no way to group the Projects belonging to the same customer.

**How it preserves existing behavior**: `POST /audits { url }` still works with no new required field. When a Project is auto-provisioned from a URL and no `clientId` is supplied, a Client is auto-provisioned the same way Projects were auto-provisioned from a URL in `F4-S01` (find-or-create by primary domain, industry defaulted to `"unknown"`). Passing an explicit `clientId` on `POST /audits`, or creating a Client explicitly via `POST /clients`, lets several Projects share one Client — the actual multi-customer capability this decision exists to enable.

**Rejected alternative**: Requiring `clientId` on every `POST /audits` call. Rejected because it would break the existing audit-creation contract for no benefit to single-customer usage, contradicting the Discovery Protocol's rule to prioritize backward compatibility.

**Scope boundary**: Contacts, billing, organizations, teams, and permissions were explicitly out of scope for this decision and are not implemented. See `docs/03_PRODUCT/FUTURE_ROADMAP.md`.

# CTO-061

**Title**: Executive Dashboard as a pure Read Model composition
**Sprint**: F6-S02
**Decision**: Implement the Executive Dashboard as an application-layer composition (`ExecutiveDashboardQueryService`) that reads exclusively from existing Read Models — the Project, Client, and Audit repositories; the Finding, AI Visibility, and Baseline History read repositories already established in `F3-S05`, `F4-S02`, and `F4-S03`; and the Optimization Planner (`generateOptimizationPlan`, see `CTO-062`). It persists nothing new and adds no new endpoint on any Business Engine.

**Why**: The objective requires an "immediate understanding" view without executing business logic or querying Business Engines directly. Composing already-computed Read Model data is the only approach consistent with both constraints, and reusing the Optimization Planner avoids a second, divergent implementation of prioritization.

**Score trend and Priority Actions**: `AiVisibilityAssessment` only ever stored a categorical status (`ready` / `needs-improvement` / `not-ready`) — no numeric score exists anywhere in the domain model. "AI Visibility Score" on the Dashboard is that same categorical value; "Score Trend" is a fixed three-value ordinal comparison of current vs. Baseline, reusing the same comparison approach already used by the Audit Comparison Service (`F4-S03`). The Dashboard's "Priority Actions" are the Optimization Plan's own `OptimizationItem[]` (see `CTO-062`), sorted by priority and capped to the top five — the Dashboard does not compute its own separate impact/effort/priority values.

**Rejected alternative**: Computing a new numeric AI Visibility score. Rejected because no such score exists anywhere in the domain model; introducing one would be new business logic invented outside a Read Model, which the objective explicitly forbids.

**Scope boundary**: Charts, filters, PDF export, dashboard widget customization, and a multi-project dashboard view were explicitly out of scope and are not implemented. See `docs/03_PRODUCT/FUTURE_ROADMAP.md`.

# CTO-062

**Title**: Optimization Planner as an application-layer projection with a dependency-aware prioritization model
**Sprint**: F6-S03
**Decision**: Implement the Optimization Planner at `apps/api/src/application/optimization/` — `generateOptimizationPlan` (a projection: Findings + Project/Audit context → `OptimizationItem[]`) and `optimization-prioritization.ts` (the prioritization model). This is the same underlying capability first implemented in this sprint under the name "Recommendation Engine"; it was renamed and extended to "Optimization Planner" / `OptimizationItem` / `OptimizationPlan` before any external consumer depended on the earlier names, so the rename replaced rather than duplicated it — `Recommendation`, `RecommendationSummary`, and `apps/api/src/application/recommendation/` no longer exist. It lives in the application layer (not presentation, where recommendation generation originated as a single-consumer helper in `F2-S14`) because both the Audit response (`audit-summary.view.ts`) and the Executive Dashboard (`F6-S02`, see `CTO-061`) consume it — presentation-layer code depends on it, never the reverse.

`OptimizationItem` carries `title`, `description`, `rationale` (business rationale), `expectedImpact`, `estimatedEffort`, `priority`, `status`, `supportingFindingIds`, `projectId`, and `auditId`. The Executive Dashboard's Priority Actions are this same `OptimizationItem[]`, sorted by priority and capped to the top five — no separate Dashboard-side type or heuristics.

**Prioritization model**: Priority is a deterministic composite of four inputs, each a `low`/`medium`/`high` level:
- **Expected impact** — derived from the Audit's overall `AiVisibilityAssessment.status` (`not-ready` → high, `needs-improvement` → medium, `ready` → low).
- **Estimated effort** — derived from the count of Findings an Optimization Item groups (1 → low, 2–3 → medium, 4+ → high).
- **Confidence** — currently always `high`: the Rule Engine only ever returns a definitive pass/fail outcome, never a partial or uncertain one, so there is no real signal to differentiate confidence today. The model still takes it as an explicit input so a future Rule Engine capable of partial/uncertain outcomes needs no redesign here.
- **Dependencies between Optimization Items** — the Workflow Runtime always executes Business Engines in one fixed order (discovery → crawl → inventory → analysis → entity → knowledgeGraph → aiVisibility). An Item tied to an earlier stage genuinely blocks Items tied to later stages that are also in the same plan, since later stages depend on earlier ones having actually run — so an Item's dependency weight is how many other Items in the same plan it blocks. This is read from the platform's own already-established, unchanging step order, not invented.

These four levels are scored and combined (impact weighted highest; low effort and high blocking weight both favored) into `priority`. The plan remains a projection: nothing is persisted, and everything is recomputed from Findings and Project/Audit context on every read.

**Why not expose Confidence as a field**: the acceptance criteria list the fields to expose (Title, Description, Business rationale, Expected impact, Estimated effort, Priority, Supporting Findings); Confidence is named only as a prioritization input, not a field to display, so it stays internal to the model rather than adding contract surface nothing asked to see. The same applies to the raw dependency weight.

**Rejected alternative**: Differentiating Estimated Effort or Confidence by Finding category or source engine, or inventing an unrelated dependency graph between Findings. Rejected because no such taxonomy exists anywhere in the domain model — inventing one would be fabricating data not actually produced by any Business Engine. The pipeline execution order, by contrast, is real and already fixed by the Workflow Runtime.

**Scope boundary**: AI-generated recommendations, task lifecycle, assignments, an approval workflow, and automatic implementation were explicitly out of scope and are not implemented. See `docs/03_PRODUCT/FUTURE_ROADMAP.md`.

# CTO-063

**Title**: Optimization Campaign as a persisted execution-tracking aggregate, distinct from the (unpersisted) Optimization Plan
**Sprint**: F6-S04
**Decision**: Implement `OptimizationCampaign` and `OptimizationAction` as genuinely persisted entities (`optimization_campaigns`, `optimization_actions` tables), at `apps/api/src/domain/campaign/`, `application/campaign/`, `infrastructure/campaign/`, `presentation/campaign/`. This is a deliberate architectural contrast with `CTO-062`: the Optimization Plan is a stateless projection recomputed on every read and never persisted, while a Campaign exists specifically to track the *execution* of one such plan over time — a Campaign only makes sense as something with a lifecycle and a durable identity, so unlike the Plan it must be a real aggregate. Both entities follow the exact persisted-aggregate pattern `Audit` established in `F3-S01`: a private constructor, `fromPersistence`, immutable state-transition methods that validate against a fixed transition table and throw on an illegal move, with the Prisma repository fetching the current entity, calling its transition method, and persisting the result — never writing a status directly.

`OptimizationCampaign` belongs to exactly one Project (`projectId`, required) and lifecycle `draft → active → completed → archived`. `OptimizationAction` belongs to exactly one Campaign and lifecycle `pending → in-progress → completed → verified`; each Action carries `projectId` and `auditId` directly (not merely derivable through its Campaign), per the acceptance criteria's explicit reference requirement. All lifecycle transitions on both entities are manual, agency-triggered (`POST /campaigns/:id/status`, `POST /campaigns/:campaignId/actions/:actionId/status`, each `{ status }` validated against the fixed forward-only transition table) — nothing advances automatically, since Automation was explicitly out of scope.

**Referencing the Optimization Item without persisting it**: an `OptimizationAction` must reference the `OptimizationItem` it came from, but `OptimizationItem` (`CTO-062`) has no stable identifier of its own — it is a projection, regenerated identically every time from the same Findings and Assessment, never assigned an id. Rather than adding an `id` field to `OptimizationItem` (which would mean modifying the Optimization Planner, explicitly forbidden by this sprint), each Action snapshots the two facts that already uniquely and deterministically identify which Item produced it: `title` and `supportingFindingIds` (themselves real, persisted `Finding.id` values). Given a fixed `auditId`, `(title, supportingFindingIds)` is exactly reproducible by regenerating the plan — no new identity concept was invented, and the Planner was not touched.

**Creating a Campaign**: `CreateCampaignUseCase` finds the Project's latest completed Audit, reads its Findings and AI Visibility Assessment through the same read repositories the Dashboard and Optimization Planner already use, calls `generateOptimizationPlan` (read-only usage — the Planner's own code is untouched), and creates one `OptimizationAction` per resulting `OptimizationItem`, each starting `pending`. If the Project has no completed Audit yet, creation fails with `NoCompletedAuditError`; a plan with zero Items still produces a valid Campaign with zero Actions (not an error).

**Dashboard integration**: the Dashboard's `campaign` field is a `CampaignProgressSummary` — the Project's latest Campaign's status plus a count per Action status and a `progressPercentage` (share of Actions `verified`), computed by a pure function (`computeCampaignProgress`) shared between the Dashboard and the Campaign's own read model. The Dashboard performs no Campaign business logic of its own, consistent with `CTO-061`.

**Rejected alternative**: Deriving Campaign status automatically from its Actions' statuses (e.g., auto-completing a Campaign once every Action is verified). Rejected because it is a form of automation, and Automation was explicitly out of scope for this sprint.

**Scope boundary**: user assignments, comments, notifications, due dates, automation, and external integrations were explicitly out of scope and are not implemented. See `docs/03_PRODUCT/FUTURE_ROADMAP.md`.

# CTO-064

**Title**: Impact Assessment as a projection built entirely on the existing Audit Comparison Service
**Sprint**: F6-S05
**Decision**: Implement `ImpactAssessmentService` (`apps/api/src/application/impact-assessment/`) as a thin, unpersisted projection over `AuditComparisonService` (`F4-S03`/`CTO-062`'s sibling capability) — it does not re-read Findings or AI Visibility Assessments itself, or reimplement any diffing logic. Given an Optimization Campaign, it resolves the Project's designated Baseline Audit (`Project.baselineAuditId`, `F4-S02`) and a Verification Audit (explicit `verificationAuditId`, or the Project's latest completed Audit if omitted), calls `auditComparisonService.compare(baselineAuditId, verificationAuditId)` for the raw `FindingComparison`/`EntityComparison`/`AiVisibilityComparison`, and layers three things on top that the Comparison Service has no reason to know about: the link to a specific Campaign, a structured improvements/regressions summary, and how many of that Campaign's own Optimization Actions are objectively confirmed resolved.

**"Baseline" is the Project's Baseline, not the Campaign's source Audit**: a Campaign's `sourceAuditId` (`CTO-063`) is simply whichever Audit its Optimization Plan happened to be generated from — it can differ from the Project's actual designated Baseline. "Impact" is measured against the Project's Baseline because that is the platform's one existing, agency-controlled "before" reference point (`F4-S02`); reusing it means this sprint introduces no second, competing notion of "baseline."

**Verification workflow**: audit a Project → set its Baseline (`F4-S02`) → generate an Optimization Plan and create a Campaign from it (`F6-S03`/`F6-S04`) → work the Campaign's Actions → run a new Audit once fixes are live → request that Campaign's Impact Assessment, which compares the original Baseline against this new Audit. Nothing about this workflow is automatic; the "new Audit" step and the Impact Assessment request are both agency-triggered, matching Automation being out of scope for `F6-S04` and PDF/email delivery being out of scope here.

**Linking Actions to measurable outcomes without touching the Optimization Planner**: `OptimizationAction.supportingFindingIds` already stores real `Finding.id` values (`CTO-063`, itself `${auditId}:${ruleId}`). Since the Comparison Service's `FindingComparisonEntry` carries `ruleId` (stable across Audits) but not the audit-qualified `Finding.id`, an Action's finding IDs are matched against `resolvedFindings` by extracting the `ruleId` portion using the Action's own recorded `auditId` as the known prefix — no change to the Planner, no new identity concept, just parsing an ID format the Planner already produces.

**Read Models**: `GET /campaigns/:id/impact-assessment` returns the full `ImpactAssessment` (a Read Model, nothing persisted, recomputed on every call). The Executive Dashboard's `campaignImpact` field is a smaller `ImpactAssessmentSummary` projection of the same computation — verification date, AI Visibility trend, findings resolved/introduced counts, the improvement summary, and a remaining-opportunities count (the Baseline's still-failing Findings that are still failing in the Verification Audit, i.e. `comparison.findings.unchangedFindings` filtered to `outcome: 'fail'` — already computed by the Comparison Service, not recomputed). If no Campaign exists yet, or an assessment cannot yet be produced (for example no Baseline set), the Dashboard shows `null` rather than failing the whole Dashboard request.

**Local refactor**: `VisibilityScoreTrend` moved from `executive-dashboard.ts` into `ai-visibility.ts`, since it is now shared by the Dashboard and the Impact Assessment contracts and belongs with the AI Visibility vocabulary it describes, not with either specific consumer. `PROJECT_REPOSITORY`'s provider registration was extracted into a new `ProjectRepositoryModule` (mirroring the `Audit`/`Client`/`Campaign` repository-module pattern already established), so the Campaign module can depend on the Project repository directly instead of importing all of `ProjectModule`.

**Rejected alternative**: Scoping the "before" snapshot to the Campaign's `sourceAuditId` instead of the Project's Baseline. Rejected because it would silently produce two different, disconnected notions of "the starting point" for the same Project, contradicting the Baseline concept `F4-S02` already established as the platform's single reference point.

**Scope boundary**: PDF reports, email delivery, AI narrative generation, trend analysis (more than two Audits), and multi-campaign comparisons were explicitly out of scope and are not implemented. See `docs/03_PRODUCT/FUTURE_ROADMAP.md`.

# CTO-065

**Title**: Optimization Knowledge Base as a static, code-defined, versioned catalog — the Optimization Planner's only source of optimization judgment
**Sprint**: F6-S06
**Decision**: Introduce `apps/api/src/application/optimization-knowledge-base/` as the canonical repository of optimization knowledge: an `OptimizationRuleDefinition` per Analysis Rule id (`ruleId`, `enabled`, an append-only `versions` array of immutable `OptimizationRuleVersion` entries — category, severity, business rationale, resolution strategy, expected impact, evidence references, published date), seeded today for the three Analysis Rules that actually exist (`discovery-execution`, `crawl-execution`, `inventory-execution`; see `services/analysis/src/rules/rule-registry.ts`). A rule's current version is always its versions array's last entry; publishing a new version means appending, never mutating an existing entry, so old versions remain a permanent, immutable historical record even after being superseded. `resolveOptimizationRule(ruleId)` returns the current version, or `null` if the rule is unknown or disabled — the Knowledge Base's only public interface the Planner depends on.

**"Optimization Rule" is a distinct concept from the Analysis Rule Engine's `Rule<TInput>`** (`packages/rules`, used since `F2-S08`): an Analysis Rule evaluates a Finding's pass/fail outcome from engine output; an Optimization Rule is knowledge about what to *do* once a Finding has already failed. They share a `ruleId` (an Optimization Rule is keyed by the Analysis Rule id it provides guidance for) but are otherwise unrelated types, in unrelated packages, evaluated at unrelated times. Business Engines and the Rule Engine were not modified.

**The Planner no longer embeds optimization logic**: `generateOptimizationPlan` (`CTO-062`) previously hardcoded its title/description/rationale as string templates and derived `expectedImpact` uniformly for an entire plan from the Audit's overall `AiVisibilityAssessment.status`. It now resolves each Finding's matching Optimization Rule and takes `description` from `resolutionStrategy`, `rationale` from `businessRationale`, and — the more significant change — `expectedImpact` from the Rule itself, not the assessment. This is more accurate: whether an issue matters is a property of *what kind of issue it is* (a Rule), not of how the Audit turned out overall. A Finding whose `ruleId` has no matching enabled Optimization Rule produces no Optimization Item — the Knowledge Base is now the single gate on what counts as "actionable," matching "Rules can be enabled or disabled" actually doing something observable. `estimatedEffort`, `confidence`, and dependency weight remain Planner-computed, since those describe the specific plan instance (how many Findings, what else is in this particular plan), not the abstract Rule.

**Read Model change**: every `OptimizationItem` gained `optimizationRuleId` and `optimizationRuleVersion`, so "every Optimization Item references one or more Optimization Rules" (today, in this design, exactly one) is externally visible on the Read Model, not just an internal implementation detail.

**Dashboard consistency**: the Dashboard's `criticalFindings`/`opportunities` split (`F6-S02`) previously used the same now-removed uniform assessment-status derivation as the old Planner. It now counts directly from the same `OptimizationItem[]` the Priority Actions section displays (`expectedImpact === 'high'` vs. not), so the two Dashboard sections can never disagree about which issues are critical — one Knowledge Base lookup, not two independent derivations of "how bad is this."

**Why code-defined, not a database table with an editor**: a Rule editor UI and external synchronization were both explicitly out of scope, and nothing in this sprint calls for runtime-authored rules — the catalog is a curated, reviewed artifact like the Rule Set itself (`F3-S08`) or the Product Capability Catalog (`F3-S11`), not user data. This also keeps rule immutability structurally guaranteed (TypeScript literals in source control, reviewed like any other code change) rather than requiring database-level enforcement.

**Rejected alternative**: Persisting Optimization Rules in the database with mutable rows. Rejected because "Rules must be immutable once published" is far easier to guarantee for source-controlled, code-reviewed literals than for database rows that would need application-level write protection to achieve the same guarantee, and a persisted, editable rule table is most of the way to the explicitly out-of-scope Rule editor UI.

**Scope boundary**: AI-generated rules, a rule editor UI, a rule marketplace, and external synchronization were explicitly out of scope and are not implemented. See `docs/03_PRODUCT/FUTURE_ROADMAP.md`.

# CTO-066

**Title**: Reasoning Engine as a structured-facts-only explanation layer, attached to every Optimization Item
**Sprint**: F6-S07
**Decision**: Implement `apps/api/src/application/reasoning/build-reasoning-model.ts` — a pure function producing a `ReasoningModel` for one Optimization Item from data the Planner already has in hand at generation time: the triggering Finding, the resolved Optimization Rule (`CTO-065`), the Audit's `AiVisibilityAssessment`, and the Audit's Knowledge Graph. `generateOptimizationPlan` (`CTO-062`) now attaches `reasoning: ReasoningModel` to every `OptimizationItem` it produces. Nothing about the Reasoning Engine involves an LLM, natural-language generation, or free-form text — every field is either a direct copy of already-real, already-computed data, or a lookup into a small fixed vocabulary. This required re-adding `AiVisibilityAssessment` and `KnowledgeGraphResult` as `generateOptimizationPlan` parameters (removed in `CTO-065` when `expectedImpact` moved to being Rule-sourced) — they serve reasoning now, not priority.

**The seven required Reasoning Model fields, and where each genuinely comes from**:
- **Triggering Findings** — the Finding's own `id`/`ruleId`/`category`/`sourceEngine`/`outcome`, already real data, just carried forward.
- **Applied Optimization Rules** — the resolved `OptimizationRuleVersion`'s `ruleId`/`version`/`category`/`severity` (`CTO-065`).
- **Supporting evidence** — the Rule's own `evidenceReferences` (`CTO-065`) resolved against the Finding's actual `evidence` object; a reference with no matching value is dropped rather than fabricated.
- **Knowledge Graph facts** — the Audit's `AiVisibilityAssessment.graphCompleteness`/`entityCoverage`/`relationshipCoverage`, which the AI Visibility Engine itself already computes from the Knowledge Graph — always populated, since every Optimization Item exists because these dimensions are not fully "ready."
- **Entity relationships (when applicable)** — Knowledge Graph relationships whose source or target node name appears among the Finding's own evidence values. Every Analysis Rule today is `category: 'execution'`, whose evidence (`{status}`) never names an entity, so this is honestly empty for every Optimization Item that exists today — not because the field is unimplemented, but because there is nothing genuine to report. The matching mechanism itself is real and was verified against a synthetic scenario where an evidence value did name a node, which correctly matched, before observing it correctly returns empty on today's real rule set.
- **Expected outcome** — the Rule's own `expectedImpact`, framed as a `{ impactLevel, targetDimension: 'ai-visibility' }` fact; not a new invented prediction.
- **Confidence** — the Planner's existing `deriveConfidence()` (`CTO-062`), reused directly, not recomputed.
- **Assumptions** — drawn from a small closed `AssumptionCode` enum with a fixed, non-interpolated description per code (`BINARY_RULE_OUTCOME`, `UNIFORM_RULE_APPLICABILITY`, always present; `FIXED_PIPELINE_ORDER`, present only when the Item's dependency weight is non-trivial) — a static lookup table, the same pattern as an HTTP status reason phrase, not text generated per instance.
- **Rule version** — carried inside "Applied Optimization Rules" rather than as a separate top-level field, since it is meaningless without the Rule it versions.

**Why this is not "free-form text"**: every string in a `ReasoningModel` is either copied verbatim from an already-existing structured value (a Finding field, a Rule field, an Assessment field, a Knowledge Graph node/relationship field) or selected from a small fixed vocabulary with a description that does not vary per instance. Nothing is composed, templated with per-instance interpolation, or generated by a model.

**Exposure**: no new endpoint. `ReasoningModel` is now simply a field on `OptimizationItem`, which is already exposed through the Audit response (`optimizationPlan`) and the Executive Dashboard's `priorityActions` (`CTO-061`) — "expose through dedicated Read Models" is satisfied by the Read Models the Reasoning Model was added to, not a new one.

**Rejected alternative**: A new `KnowledgeGraphReadRepository`-free design that skipped Entity relationships whenever a Dashboard/Campaign call site lacked graph data on hand. Rejected in favor of adding `KnowledgeGraphReadRepository` (mirroring `FindingReadRepository`/`EntityReadRepository`/`AiVisibilityReadRepository`, `F3-S05`/`F6-S03`) to every call site, so the same Reasoning Model is produced identically regardless of which Read Model requested it — reasoning must be reproducible, not caller-dependent.

**Scope boundary**: LLM integration, a conversational interface, natural language generation, and AI explanations were explicitly out of scope and are not implemented. See `docs/03_PRODUCT/FUTURE_ROADMAP.md`.

# CTO-067

**Title**: AI Context as an apps/api-internal type, not a Contract Layer export — a pure composition of everything already built
**Sprint**: F7-S01
**Decision**: Implement `AiContextBuilderService.build(projectId)` at `apps/api/src/application/ai-context/`, returning a frozen `AiContext` object. Unlike every prior F4–F6 Read Model, `AiContext` is defined entirely inside `apps/api` (`application/ai-context/ai-context.ts`), not exported from `packages/contracts`. This is deliberate, not an oversight: the Contract Layer (`docs/01_ARCHITECTURE/DEPENDENCY_MODEL.md`) exists to let data cross a system boundary — an HTTP response, a Dashboard field. This sprint explicitly forbids every boundary `AiContext` could cross (no OpenAI/Anthropic/Gemini integration, no prompt generation, no chat interface, no streaming) and does not ask for a Dashboard field or a controller endpoint — "expose the Context through an internal application service," not a Read Model. There is nothing on the other side of a boundary yet for a Contract Layer type to serve. `AiContext` does still reference several existing `@ai-visibility/contracts` types (`ProjectMetadata`, `ClientMetadata`, `Finding`, `KnowledgeGraphResult`, `OptimizationItem`, `CampaignMetadata`, `ImpactAssessment`) — apps/api already legitimately depends on the Contract Layer for everything else, so this is ordinary reuse, not a new boundary crossing.

**Composition, not new logic**: `AiContextBuilderService` calls only services and repositories every prior F4–F6 sprint already built and already verified — `ProjectRepository`, `ClientRepository`, `AuditRepository`, `FindingReadRepository`, `AiVisibilityReadRepository`, `KnowledgeGraphReadRepository` (`F6-S07`), `CampaignQueryService` (`F6-S04`), `ImpactAssessmentService` (`F6-S05`), `generateOptimizationPlan` (`F6-S03`/`F6-S06`), and `listOptimizationRules`/`currentVersion` (`F6-S06`). It computes nothing new; it only assembles. This mirrors `ExecutiveDashboardQueryService` (`CTO-061`) and `ImpactAssessmentService` (`CTO-064`), both pure compositions over already-existing Read Models, extended one step further to be genuinely comprehensive rather than dashboard-shaped.

**What the eleven required aggregation items map to**: Project → `ProjectMetadata`. Client → `ClientMetadata`. Latest Audit → a dedicated `AiAuditFact` (id, url, status, timestamps, AI Visibility status) that deliberately excludes `AuditMetadata.executionHistory` — Workflow step timing and error codes are Workflow Runtime *operational* detail, not a business fact about the Project, so they are the one thing this sprint's "excludes infrastructure concerns" acceptance criterion actually excludes. Baseline → a dedicated `AiBaselineFact` (`auditId`, `setAt`) reusing `Project.baselineAuditId`/`baselineSetAt` (`CTO-...F4-S02`). Knowledge Graph → the existing full `KnowledgeGraphResult`. Findings → the existing full `Finding[]`. Optimization Plan → `OptimizationItem[]` (`CTO-062`). Optimization Campaign → `CampaignMetadata` (`CTO-063`). Impact Assessment → `ImpactAssessment` (`CTO-064`), or `null` if it cannot yet be produced (for example no Campaign, or no Baseline) — never an error, since the Context describes whatever currently exists. Reasoning Models → already present as `OptimizationItem.reasoning` (`CTO-066`); no separate top-level field, since flattening it out again would duplicate what the Optimization Plan already carries. Optimization Rules → `optimizationRules: OptimizationRuleVersion[]`, the full *enabled* Knowledge Base catalog (`CTO-065`) via `listOptimizationRules()` — distinct from the specific Rules already referenced inside the Optimization Plan, since an AI Consultant benefits from knowing the complete available vocabulary of optimization knowledge, not only what happens to be currently triggered.

**Immutability**: `Object.freeze()` on the returned object, the same shallow-freeze convention `AuditSnapshot` already established (`F2-S15`) — freezing top-level assignment is what this codebase has always meant by "immutable," and this sprint does not change that bar.

**Versioning**: a static `contextVersion` constant (`AI_CONTEXT_VERSION = '1.0.0'`) stamped onto every generated Context, describing the *shape* of `AiContext` itself — bumped by hand whenever the type changes — the same "versioned document" pattern as an API response version, distinct from (and compatible with) the individual version markers each nested fact already carries on its own (`Finding.ruleVersion`, `OptimizationItem.optimizationRuleVersion`).

**Rejected alternative**: Exporting `AiContext` from `packages/contracts` now, anticipating the HTTP endpoint or Dashboard field a future sprint might add. Rejected because nothing currently consumes it across a boundary, and per the Discovery Protocol, favoring the option that minimizes footprint means not building a Contract Layer surface for a consumer that does not exist yet — that decision belongs to whichever future sprint actually adds the consumer.

**Scope boundary**: OpenAI integration, Anthropic integration, Gemini integration, prompt generation, a chat interface, and streaming were explicitly out of scope and are not implemented. See `docs/03_PRODUCT/FUTURE_ROADMAP.md`.

# CTO-068

**Title**: AI Conversation Orchestrator as a pure four-stage pipeline, provider-abstracted behind a Null Object so it is genuinely testable before any real provider exists
**Sprint**: F7-S02
**Decision**: Implement `AiConversationOrchestratorService.orchestrate(request)` at `apps/api/src/application/ai-conversation/`, entirely inside `apps/api` for the same reason `AiContext` is (`CTO-067`) — nothing crosses a system boundary yet (no Chat UI, no controller). The pipeline is `ConversationRequest → (resolve AiContext, apply Conversation Policies) → AiRequest → [AiProvider port] → AiResponse → ConversationResponse`, giving every model term the ticket names a distinct, non-redundant role: `ConversationSession`/`ConversationRequest` are what a caller provides; `AiRequest` is the context-enriched, provider-ready payload the Orchestrator assembles; `AiResponse` is what a Provider returns; `ConversationResponse` is what the Orchestrator returns to the caller, wrapping the session and (if a Conversation Policy rejected the request) a structured `PolicyRejection` instead of a response.

**Enforcing "must not access repositories directly / must not contain business logic"**: the Orchestrator's constructor takes exactly two dependencies — `AiContextBuilderService` (`CTO-067`) and the `AiProvider` port — no `*_REPOSITORY` token, matching the acceptance criteria literally rather than by convention. Its own logic is limited to: resolve one `AiContext`, run a fixed list of `ConversationPolicy` objects, assemble one `AiRequest`, call the provider, wrap the result. It computes nothing.

**Conversation Policies are structural, not business rules**: `SupportedIntentPolicy` checks the intent type against a fixed enum (`ConversationIntentType`); `RequireCompletedAuditPolicy` checks `context.latestAudit !== null`. Neither interprets Project content or computes a judgment — both are presence/membership checks against already-resolved `AiContext`, the same kind of structural gate `ENGINE_EXECUTION_STANDARD.md`-style validation already uses elsewhere in this codebase, never "business logic" in the sense Findings/Optimization Rules/Reasoning already own. A rejected policy short-circuits before `AiRequest` is even assembled, returning `ConversationResponse.status = 'rejected'` rather than throwing — a policy decision is an expected outcome of orchestration, not an exceptional failure.

**The provider abstraction, and why a Null Object exists despite "Do not implement: OpenAI, Anthropic, Gemini"**: `AiProvider` (`complete(request): Promise<AiResponse>`) is the port; `NoOpAiProvider` (`apps/api/src/infrastructure/ai-conversation/`) is the only implementation, and is not OpenAI, Anthropic, or Gemini — it deterministically returns `{ status: 'unavailable', content: null }` without any network call, any text generation, or any provider-specific logic. Its purpose is structural: "the provider interface must support future integrations without changing the orchestration layer" is only a verifiable claim if the Orchestrator actually calls *some* implementation of the port end-to-end today; without one, `Repository builds successfully` would be the only thing this ticket could actually prove. Wiring a real provider later (a future sprint) means adding one new class implementing `AiProvider` and rebinding `AI_PROVIDER` in `ProjectModule` — the Orchestrator itself does not change, which is the acceptance criterion this decision exists to satisfy.

**Rejected alternative**: Leaving `AI_PROVIDER` unbound so the Orchestrator cannot be instantiated at all until a real provider ships. Rejected because it would make "Orchestrator resolves AI Context correctly" — an explicit Self Validation requirement — unverifiable, and because a correctly-typed but perpetually-unimplemented DI token is a worse signal of "provider independent" than a working Null Object that visibly does nothing.

**Scope boundary**: OpenAI, Anthropic, Gemini, streaming, a Chat UI, and conversation persistence were explicitly out of scope and are not implemented — `ConversationSession` is a caller-supplied value object with no server-side store, not a persisted entity. See `docs/03_PRODUCT/FUTURE_ROADMAP.md`.

# CTO-070

**Title**: AI Daily Briefing as a Read Model composed across every active Project's AI Context — workspace-scoped, not chat-scoped
**Sprint**: F7-S04
**Decision**: Implement `AiDailyBriefingQueryService.build()` (`apps/api/src/application/ai-briefing/`), exposed via `GET /briefing/daily` (`apps/api/src/presentation/briefing/`). Unlike `AiContext` (`CTO-067`) and the Orchestrator (`CTO-068`), this ticket explicitly requires the Briefing be "exposed through Read Models," so it follows the `ExecutiveDashboardQueryService` (`CTO-061`) pattern from the start — a Read Model composition service with a real controller — rather than starting as an apps/api-internal service. `BriefingModel`/`BriefingItem`/`BriefingEvidenceFact`/`BriefingItemCategory` are exported from `packages/contracts/src/ai-briefing.ts`, the same "Contract Layer only exists once something crosses a boundary" reasoning as `CTO-067`/`CTO-069`, now satisfied immediately since the objective itself names the boundary (a Read Model, and "generated automatically on workspace load").

**Workspace-scoped, not per-Project**: `AiDailyBriefingQueryService` lists every `Project` whose `Client.status === 'active'` (`ClientRepository.findAll()` / `ProjectRepository.findAll()`), then calls the existing `AiContextBuilderService.build(projectId)` (`CTO-067`) once per active Project and composes one `BriefingItem[]` per Context. This is the first F7 ticket to aggregate across Projects rather than operate on one — the ticket's "across their active Clients and Projects" language is what makes "active" mean `Client.status === 'active'`, since `Project` itself carries no status field.

**Six categories, each a pure derivation from one Project's already-computed `AiContext` — no new business logic invented**: `apps/api/src/application/ai-briefing/briefing-items.ts` maps each of the ticket's six required categories to fields already established by prior F6/F7 sprints, the same "compose, don't compute" discipline as `CTO-067`/`CTO-069`: Critical Findings → `context.findings` where `severity !== 'none'` (`F3-S04`). Campaigns Awaiting Verification → `context.optimizationCampaign.status === 'completed'` — the one state between "all actions done" and "archived" (`CTO-063`'s `draft→active→completed→archived` machine), meaning the work is finished but not yet confirmed/closed. AI Visibility Regressions → `context.impactAssessment.regressions` (`CTO-064`). High-Impact Opportunities → `context.optimizationPlan` items with `priority === 'high'` (`CTO-062`), reusing `item.reasoning` (`CTO-066`) directly for evidence and confidence. Recently Completed Improvements → `context.impactAssessment.improvements` (`CTO-064`). Projects Requiring Immediate Attention → a per-Project rollup item, emitted only when a Project has at least one critical Finding, one regression, or `latestAudit.aiVisibilityStatus === 'not-ready'` — the only category that synthesizes across the other signals rather than reading one field directly, and it does so by counting, not by inventing a new judgment threshold.

**Every item carries the five required facts** (`Reason`, `Business Impact`, `Supporting Evidence`, `Recommended Next Action`, `Confidence`) as explicit `BriefingItem` fields, populated by deterministic string templating over `AiContext` data — never free-form generation, matching `F6-S07`'s "structured facts only" bar and `F7-S03`'s `StructuredFactAiProvider` precedent (`CTO-069`). `confidence` reuses each fact's own already-computed confidence where one exists (`OptimizationItem.reasoning.confidence`) and otherwise `'high'`, the same rationale `deriveConfidence()` (`optimization-prioritization.ts`) already established: the Rule Engine only ever returns definitive pass/fail, so there is no meaningful uncertainty to express for Finding- or Assessment-derived facts.

**Prioritization strategy**: `apps/api/src/application/ai-briefing/briefing-prioritization.ts` sorts the combined item list by a fixed category rank — `project-attention` > `ai-visibility-regression` > `critical-finding` > `campaign-awaiting-verification` > `high-impact-opportunity` > `recent-improvement` — then by `confidence` within a category, mirroring `sortByPriority` (`optimization-prioritization.ts`, `F6-S03`). Negative/urgent signals surface first, "Recently Completed Improvements" last — satisfying "Briefing prioritizes Projects requiring attention" as an explicit, inspectable ordering rather than an implicit one.

**"Must not call any LLM" / "structured Briefing Model that can later be rendered by any AI provider"**: `AiDailyBriefingQueryService` has no dependency on `AiProvider`, `AI_PROVIDER`, or the Conversation Orchestrator (`CTO-068`) at all — it is a pure, provider-independent Read Model, exactly as `AiContext` is. Any future provider (real or `StructuredFactAiProvider`) can render `BriefingModel` into prose without this service changing, the same non-goal `CTO-067` already established for `AiContext` itself.

**Automatic generation on workspace load**: `apps/web/app/daily-briefing.tsx` (`DailyBriefing`, mounted at the top of `apps/web/app/page.tsx`) fetches `GET /briefing/daily` in a `useEffect` on mount — no button, no user action required — satisfying "generated automatically on workspace load" the same way `F7-S03`'s Chat is deliberately question-triggered instead.

**Rejected alternative**: Scoping the Briefing to a single Project (matching `AiContext`'s existing shape) and only aggregating client-side. Rejected because the objective is explicitly a workspace-level "across their active Clients and Projects" view, and computing a real cross-Project aggregate server-side is what makes "exposed through Read Models" and "prioritizes Projects requiring attention" verifiable as backend behavior rather than emergent UI behavior.

**Scope boundary**: Notifications, emails, push alerts, scheduling, and cross-account summaries were explicitly out of scope and are not implemented — the Briefing is generated fresh on every `GET /briefing/daily` call, never persisted or pushed. See `docs/03_PRODUCT/FUTURE_ROADMAP.md`.

# CTO-071

**Title**: Optimization Cycle as a genuinely persisted grouping aggregate — Audits, Campaigns, and the computed Plan/Impact Assessment all reference one Cycle, none of it duplicated
**Sprint**: F7-S05
**Decision**: Implement `OptimizationCycle` (`apps/api/src/domain/optimization-cycle/`) as a persisted aggregate — `Planned → Running → Verification → Completed`, the same fixed-table transition pattern as `Campaign` (`CTO-063`) and `Audit`. `OptimizationCycle` itself stores only what the ticket lists — `id`, `projectId`, `goal`, `status`, `startDate`, `endDate`, `createdAt` — and nothing an Audit, Plan, or Campaign already owns. The relationship runs the other way: `AuditRequest.cycleId` and `OptimizationCampaign.cycleId` are new required foreign keys (`packages/database/prisma/schema.prisma`, migration `20260726130949_optimization_cycle`), so a Cycle groups its work by being referenced, never by holding a duplicate list of IDs — directly satisfying "do not duplicate data already owned by Audits, Plans or Campaigns; reference existing entities."

**"Current phase" is `status` under a second name, not a second state machine**: the ticket lists both "Status" and "Current phase" as fields the Cycle "must contain," but the Lifecycle section it also provides has exactly four values — the same four `Status` already needs. Inventing an independent "phase" dimension would be new, undocumented business logic with no acceptance criterion driving its values. `OptimizationCycle.currentPhase` is a computed getter that returns `status` (`optimization-cycle.entity.ts`); `OptimizationCycleMetadata.currentPhase` is the same value surfaced as its own JSON field, so API consumers see two fields as the ticket asked, backed by one column, one machine.

**`startDate`/`endDate` are observed, not planned, following the `Campaign.activatedAt`/`completedAt` precedent**: both are `null` until reached — `startDate` is set when the Cycle transitions `planned → running`, `endDate` when it transitions `verification → completed`. This reads "a measurable business period" as the actual start and end of doing the work (only measurable once it happens), and mirrors the one nullable-until-reached timestamp convention every other Interface Layer aggregate in this codebase already uses, rather than asking a caller to guess a date range up front.

**Auto-provisioning an Audit's Cycle, the same way Client/Project already auto-provision (`CTO-059`)**: `EnsureActiveCycleUseCase` (`apps/api/src/application/optimization-cycle/`) runs inside `CreateAuditUseCase` — apps/api application layer, not a Business Engine or the Workflow Runtime, so this is in scope despite "do not modify Business Engines" / "do not modify Workflow Runtime." It finds the Project's latest Cycle; if none exists, or the latest is `completed` (a closed business period), it creates a new one and immediately starts it (an Audit is about to run inside it); if the latest is still `planned`, it starts that one; a `running` or `verification` Cycle is reused as-is. This keeps `POST /audits { url }` working with no new required field — the same backward-compatibility bar `CTO-059` set for Client — while guaranteeing "every Audit belongs to one Optimization Cycle" is true for every Audit, not just ones created through a new endpoint. `POST /projects/:id/cycles` still exists for deliberately planning a Cycle (with a `goal`) ahead of time, and `POST /cycles/:id/status` (mirroring `CampaignController`'s `POST /campaigns/:id/status`) drives the Planned→Running→Verification→Completed transitions explicitly — nothing advances on a timer, satisfying "do not implement: ... automation."

**The computed Plan and Impact Assessment reference a Cycle without persisting one**: neither `OptimizationItem` (the Optimization Plan) nor `ImpactAssessment` is a database row (`CTO-062`, `CTO-064`) — both are projections regenerated on demand. Each now carries a `cycleId` field populated from the Audit or Campaign already driving that computation (`OptimizationPlanContext.cycleId`, threaded through all four existing call sites — `audit-summary.view.ts`, `ExecutiveDashboardQueryService`, `CreateCampaignUseCase`, `AiContextBuilderService`; `ImpactAssessment.cycleId` from `campaign.cycleId` inside `ImpactAssessmentService.assess`). This is a reference to an id already resolved by existing code, not new computation — the same "compose, don't duplicate" discipline `CTO-067` and `CTO-070` already established for `AiContext` and the Daily Briefing.

**Dashboard's current Cycle status**: `ExecutiveDashboard.currentCycle` (`DashboardCycleOverview`, `packages/contracts/src/executive-dashboard.ts`) is populated by `ExecutiveDashboardQueryService` calling the new `OptimizationCycleQueryService.getCurrentByProjectId` — one more Read Model composed in, following the exact pattern `CTO-061` established for every other Dashboard section; the Dashboard computes nothing itself.

**Rejected alternative**: Making `AuditRequest.cycleId` and `OptimizationCampaign.cycleId` nullable to sidestep an auto-provisioning use case. Rejected because the acceptance criteria state "every Audit belongs to one Optimization Cycle" and "every Optimization Campaign belongs to one Optimization Cycle" without qualification — a nullable column would make that claim false for any Audit created before a Cycle existed, and this codebase's existing precedent (`CTO-059`'s Client auto-provisioning) already shows the correct fix is auto-provisioning at the boundary, not relaxing the constraint.

**Scope boundary**: Billing, contracts, invoices, recurring scheduling, and automation were explicitly out of scope and are not implemented — every Cycle transition is caller-triggered via `POST /cycles/:id/status`, exactly like `Campaign`. See `docs/03_PRODUCT/FUTURE_ROADMAP.md`.

**Sprint**: F7-S06

The ticket says "Report exposed through an application service" — not "Read Model" (`F7-S04`'s explicit HTTP-endpoint language) and not any UI/self-validation requirement (SELF VALIDATION here lists only "API builds," no "Web builds," unlike every F7 ticket since `F7-S03`). **Ten required sections, each composed from already-real data, nothing recomputed**: Executive Summary and Initial Situation are deterministic templated strings over already-resolved facts (Cycle goal/status, initial Audit's AI Visibility status, Impact Assessment counts) — the same "structured facts only" discipline `F6-S07`/`F7-S03`/`F7-S04` already established, not natural-language generation. **Rejected alternative**: Adding an HTTP endpoint and web UI now, matching the `F7-S03`/`F7-S04` pattern. Rejected because this ticket's SELF VALIDATION and TASKS are silent on both, and "Do not implement: ... Export formatting" alongside "independent of presentation format" reads as this ticket deliberately stopping at the Report Model — presentation is a later concern. Verified instead via `NestFactory.createApplicationContext` calling the service directly, the same internal-service testing pattern used for `AiContextBuilderService` and `AiConversationOrchestratorService` before either had a consumer.

**Scope boundary**: PDF/DOCX/slide generation, branding, email delivery, scheduling, and export formatting were explicitly out of scope and are not implemented — the Report is a plain structured object, regenerated fresh on every `build(cycleId)` call, never persisted or rendered.
